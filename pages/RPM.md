- It is a low-level package manager for Linux that works with `.rpm` files, which represent "packages".
- RPM recognizes two types of packages:
	- Binary package: contains prebuilt software to be installed
	- Source package: contains source code and instructions for building and installing
	- A common convention is that binary package files are suffixed with `.<arch>.rpm` (e.g. `.x86_64.rpm`) while source package files are suffixed with `.src.rpm`.
- Note that `rpm` only works with local packages - those that are already installed, or those represented by local `.rpm` files. It has no ability to interact with remote packages (e.g. searching remote package repositories or downloading + installing packages) - for that you'd need a higher-level package manager tool like [[DNF]].
- In RPM, a package is uniquely identified by its name, epoch, version, release, and architecture (NEVRA).
	- For example, RPM will allow you to install two packages side by side that are the same name/epoch/version/release but built for different architectures.
- ## Dependencies
	- RPM recognizes [dependencies](https://rpm-software-management.github.io/rpm/man/rpm-dependencies.7) between packages, although it cannot automatically resolve them.
	- In the RPM system, dependencies are represented through "capabilities":
		- A single package can provide one or more named capabilities.
		- Packages can also require one or more capabilities, which must be provided by other packages.
	- Packages can provide several different types of capabilities:
		- A package automatically provides a capability that just consists of the package name, so that other packages can depend on it in its entirety.
		- It can also provide any arbitrary string as a capability, such as `"webserver"`.
		- It can provide filepaths as capabilities, such as `/usr/bin/python3`.
		- Several capabilities that are autogenerated by `rpmbuild`.
- ## [Structure](https://en.wikipedia.org/wiki/RPM_Package_Manager#Binary_format) of a `.rpm` file
	- A `.rpm` file consists of four sections:
		- The lead: identifies the file as a `.rpm` file
		- The signature: can be used to verify integrity/authenticity
		- The header: contains package metadata, such as name, version, architecture, dependency packages, etc
		- The payload: the actual package contents to install
			- This is almost always shipped as a single archive file, e.g. a `cpio` file
- ## RPM Architecture
	- RPM uses a single "database" on your machine that records which RPM packages are tracked/installed.
		- By default, this database lives at `/var/lib/rpm` off of the filesystem root.
		- You can have multiple databases, though - `rpm --root /tmp/other_root` tells `rpm` to use the database at `/tmp/other_root/var/lib/rpm` instead.
			- `--root` also determines where the files of installed packages end up, e.g. at `/tmp/other_root/usr/share/doc/my_package/README`.
			- You can also use `--dbpath` to only alter the location of the database, but not the root install path.
- ## Helpful Commands
	- ### Querying
		- Print the package name of a local `.rpm` file:
		  ```
		  rpm -qp my_package.rpm
		  ```
		- List the files contained in a local `.rpm` file:
		  ```
		  rpm -qpl my_package.rpm
		  ```
		- List the capabilities that a local `.rpm` file depends on:
		  ```
		  rpm -qp --requires my_package.rpm
		  ```
		- List which packages depend on a capability:
		  ```
		  rpm -q --whatrequires some-capability
		  ```
		- List the capabilities that a local `.rpm` file provides:
		  ```
		  rpm -qp --provides my_package.rpm
		  ```
		- List which packages provide a capability:
		  ```
		  rpm -q --whatprovides some-capability
		  ```
	- ### Modifying
		- Install a package from a local `.rpm` file:
		  ```
		  rpm -i my_package.rpm
		  ```
		- Uninstall ("erase") an installed package by name:
		  ```
		  rpm -e my_package
		  ```
